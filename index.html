How the model works (and what it is not)
  • Stage 1 joins the transaction table with the price plan table and aggregates. Stage 2 processes the other tables, one or more tasks each.
  • Each task gets a chunk of data. Time per task is its size divided by the speed of one core (20 MB/s for the join stage, 40 MB/s for plain table work), plus 0.15 s of scheduling overhead.
  • A task needs about 2.5x its data size in memory during the join. Each core gets a share of the executor's execution memory (45% of node memory divided by cores). A task that needs more than its share spills, and spilling makes it up to 3x slower.
  • Tasks are handed to whichever core frees up first, like Spark does. The run ends when the last task ends, so one slow task sets the finish time.
  • A shuffle join moves both tables across the network at 200 MB/s per executor. A broadcast join sends the small table to every executor instead.
  • Each task writes one file, unless optimized writes is on, which targets 128 MB files.
  • This is a teaching model with round numbers. It shows direction and relative size of effects. It is not a benchmark of your real jobs.
